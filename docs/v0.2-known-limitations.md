# forge v0.2 已知缺陷清单

**记录时间**:2026-05-09 09:16 UTC
**记录方式**:本地 fixture(`D:\ClaudeProject\forge-fixture-test\`)+ 真 Claude Code 交互式会话端到端测试
**Claude Code 版本**:用户实测(2.x 当前主线,具体版本号在 fixture 测试日志里)
**fixture 起法**:`git init -q` + npm install tarball + `npx forge init --harness claude`(空 git repo,无 base commit / `.gitignore`)

本文档归档 v0.2 在真实 Claude Code 交互式会话下暴露的架构 / deploy / 模板缺陷,**作为 v0.3 plugin migration spec 的设计输入**。每条记录:

- **现象**:实测 stdout / 文件状态
- **根因**:代码 / 架构层面的真原因
- **影响**:对 forge v0.1 / v0.2 spec 价值主张的破坏程度
- **v0.3 plugin migration 期望 unblock**:plugin 化路线下如何根治

## P0 — Skill auto-trigger 完全失效(架构级)

### 现象

- fixture 起新 Claude Code 会话(superpowers plugin 已 disabled)
- 用户输入"我想做个 todo list 应用"
- Claude **没有 invoke `forge:brainstorming` 或 `forge:using-forge` skill**,直接进入 AskUserQuestion + 写代码模式
- 产物:`bin/todo.js` + `data/todos.json`(直接实现 CLI),**没写 `forge/drafts/<date>-<topic>.md`**

### 关键证据

打 `/forge:` 自动补全列表显示 18 项,其中 12 项是 SKILL.md 内容(`forge:brainstorming` / `forge:writing-plans` / `forge:using-forge` 等),description 是 SKILL.md frontmatter 的 description 字段。

但同时段 Claude Code 会话的 system reminder 中"available skills"段(用户级 plugin skill 池)**不含任何 `forge:*`**——只列了 `claude-hud:*` / `codex:*` / `update-config` / `simplify` / `init` / `review` 等 plugin / built-in skill。

### 根因

Claude Code 当前对项目级 `<project>/.claude/skills/<name>/SKILL.md` 的处理:**注册成 `/forge:<skill-name>` slash 命令,而不是注入 skill auto-trigger 池**。

也就是说,forge 的 12 个 skill 文件被识别成"另一种 slash 命令":

| 路径 | Claude Code 处理 |
|---|---|
| `.claude/commands/forge/<name>.md`(forge 6 个 commands) | ✅ 注册 `/forge:<name>` slash |
| `.claude/skills/forge-<name>/SKILL.md`(forge 12 个 skill) | ❌ **也注册 `/forge:<name>` slash**,**不进 skill auto-trigger 池** |

而 superpowers plugin 走 `~/.claude/plugins/cache/...` 路径,plugin skill 真正进 auto-trigger 池(从我自己作为 Claude Code 实例每次会话开头的 system reminder 都能看到 `superpowers:*` 出现)。

### 影响

- forge v0.1 spec §1.1 的核心价值主张("AI 在 harness 里按 forge 工作流自动跑"),**Claude Code 路径下不成立**
- `forge:using-forge` bootstrap skill 永不 auto-trigger
- 用户随便说"我想做 X",AI 按本能写代码,**完全跳过 forge 工作流**
- spike 0.5 当时(2026-05-05)在 `claude -p "..."` 单 turn 非交互模式 PASS,**交互式会话路径已回归**——可能 Claude Code 后续版本改了项目级 skill 的处理策略

**但 v0.1 / v0.2 没全炸**:显式 `/forge:brainstorm` slash 命令仍能 work。Command 内部用 `Skill(forge-brainstorming)` 显式调用 SKILL.md 也成功(SKILL.md 文件能被读,只是不进 auto-trigger)。**作为 commands 套件,forge 仍可用**——只是用户每步都得显式打命令,违反 "AI 自动按工作流跑" 原始价值主张。

### v0.3 plugin migration 期望 unblock

转 plugin 后:

- forge 的 12 skill 走 plugin marketplace cache 路径,真正进 skill auto-trigger 池
- `forge:using-forge` 在 session start 自动 trigger,把"红旗清单"注入 system prompt
- 用户说"我想做 X"时,`forge:brainstorming` 跟 `superpowers:brainstorming` 一样按 description matching auto-trigger
- 6 个 commands 仍然保留(plugin 也支持 commands)

## P1 — forge CLI 不在全局 PATH(deploy 级)

### 现象

fixture 流程中 AI 跑 `forge validate` 时:

```
$ which forge
which: no forge in (/c/Users/mzq/bin:/mingw64/bin:...)

$ forge --version
/usr/bin/bash: line 3: forge: command not found
```

AI 检测到失败后,**绕过 forge validate**,自己用"手工等价校验"代替(看 4 件套是否完整 + H1 是否存在)。

### 根因

- 用户 deploy 路径:`npm install --no-save accelerator-mzq-forge-0.2.0.tgz`(或 `pnpm dlx ...`)
- 安装位置:`<project>/node_modules/.bin/forge`
- **不在系统 PATH**,只有项目内 `npx forge` 能找到
- `.claude/commands/forge/verify.md` line 13 + `archive.md` line 13 直接写裸 `forge validate <id>` / `forge archive ...`,假设全局可用

### 影响

实测后果:**forge 严格门禁完全绕过**——
- `forge validate` 跑不了 → 没法生成 `.verify-passed` marker
- `forge archive` 跑不了 → 严格校验路径(hash 检查、verify+review marker 校验、specs sync)全部绕过
- forge v0.1 / v0.2 的核心价值主张("产物驱动 + 严格门禁"),**在当前默认 deploy 路径下不生效**

### v0.3 plugin migration 期望 unblock

- plugin 自带 forge CLI runtime(plugin 的 hooks / commands 直接用 plugin 内 bundle 的 CLI 二进制路径,不依赖用户全局 install)
- 或:plugin 安装时检测 `npm bin -g`,提示用户全局安装 + 加 PATH
- 或:plugin commands 改用 `npx forge`(npx 在 npm 7+ 优先找 project node_modules/.bin)

具体路线在 v0.3 spec 中决策。

## P2 — brainstorming skill 与 init 不匹配(行为级)

### 现象

fixture brainstorming 阶段,AI 提示:

> "brainstorming skill 默认要求 commit draft。但仓库目前没有任何 commit、`.gitignore` 也没设(`node_modules/` 等都是 untracked),我没有自动 commit"

AI 处理得很好(没自动 commit,主动问用户),但暴露了 forge init 的缺陷。

### 根因

- `forge init --harness claude` **不**做以下任一:
  - 检测 git repo 是否空(无 commit)
  - 创建最小 `.gitignore`(至少含 `node_modules/`)
  - 提示用户先做 `git commit -m "init"` 建 base
- `forge:brainstorming` skill 假设项目有 git base + `.gitignore`,要求 "draft 写完后 commit"

### 影响

- 用户体验问题(不影响功能)
- 在 fixture / 全新项目场景下,brainstorming skill 的 commit 期望与 init 状态不匹配
- 真生产场景大概率有 git base + `.gitignore`,这条问题概率较低

### v0.3 plugin migration 期望 unblock

- plugin install hook 检查 git repo 状态,空 repo 时建议 `git init` + base commit
- 或在 `forge init` 加 `--setup-gitignore` flag,默认创建 `.gitignore`
- 或 `forge:brainstorming` skill 文本改成 "**如果**仓库有 git base 历史,commit draft;无则提示用户先建 base 再 commit"

## P3 — tasks.md 过度生成(模板级)

### 现象

fixture `/forge:propose add-todo` 跑完后,产 `forge/changes/add-todo/tasks.md` **511 行**(用户原话"加 1 个 priority 字段 + `-p` flag" 这种 trivial change)。

具体重复模式:

- 每个 task 强制带 RED/GREEN/REFACTOR 三段
- 每个 task 强制带 verification 段(独立 commit 验证步骤)
- 5 个 task → 5 × ~100 行 = 500 行规模

### 根因

`forge:writing-plans` skill 模板 spec(从 superpowers `writing-plans.md` 移植)强约束:

- 必须分至少 5 task
- 每 task 必须有 RED → GREEN → REFACTOR + verification
- 不区分 trivial change vs complex feature

对小功能没有"轻量模式"。

### 影响

- 文档冗长,降低 review 体验
- AI 在 tasks.md 模板里塞太多内容,可能超出模型一次输出长度边界(本次 511 行属边缘)
- 不影响 forge 核心功能(/forge:apply 仍能按 tasks.md 跑)

### v0.3 plugin migration 期望 unblock

非 plugin 化能解决的问题。建议在 v0.3 范围内单独加:

- `forge:writing-plans` skill 加 "scale-aware mode"(based on change-id 名 / proposal 长度,决定 5 task vs 1-2 task)
- 或加 `/forge:propose --light` flag,跑简化模板

## 测试结论

✅ **作为 commands 套件,forge v0.1 / v0.2 仍可用**(显式 `/forge:*` 全链路 work)
❌ **作为 "AI auto-bootstrap 工作流",当前 Claude Code 交互模式下完全失效**
❌ **严格门禁(verify-passed / review-passed / archive)在默认 deploy 下绕过**

**v0.3 plugin migration 是恢复原始价值主张的唯一路径**(单独修 commands 模板的 P1 治标不治本——plugin 化会重做整个 commands 注册机制)。
